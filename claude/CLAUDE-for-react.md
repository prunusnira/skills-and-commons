# CLAUDE.md

이 문서는 React와 Vite 프로젝트에서 코드를 분석·수정·작성할 때 따라야 할 기본 규칙을 정의한다.

프로젝트에 이미 존재하는 규칙, 설정, 디렉터리 구조가 이 문서와 충돌한다면 기존 프로젝트의 규칙을 우선한다.

---

## 작업 디렉터리 원칙

* 별도의 Git worktree를 생성하거나 다른 worktree로 전환하지 않는다.
* 사용자가 현재 열어 둔 작업 디렉터리에서 직접 작업하여 로컬 변경사항을 바로 확인할 수 있게 한다.
* 현재 작업 디렉터리에 있는 기존 로컬 변경사항은 유지하며, 요청과 무관한 변경을 수정하거나 되돌리지 않는다.

---

## 1. 기본 원칙

* 응답과 설명은 한국어로 작성한다.
* 요청된 범위를 벗어나는 수정은 하지 않는다.
* 기존 코드 스타일과 설계 방향을 우선한다.
* 문제를 해결하기 전에 관련 코드를 충분히 확인한다.
* 확인하지 않은 내용을 추측하여 구현하지 않는다.
* 불확실한 부분은 불확실하다고 명시한다.
* 변경 범위는 가능한 작게 유지한다.
* 동작에 필요하지 않은 리팩터링을 함께 수행하지 않는다.
* 새로운 패턴이나 라이브러리를 도입하기 전에 기존 구현을 먼저 찾는다.
* 기존 구현이 정상적으로 동작하고 있다면 명확한 이유 없이 교체하지 않는다.

---

## 2. 작업 시작 전 확인

코드를 수정하기 전에 다음 항목을 확인한다.

* `package.json`
* 사용 중인 React와 Vite 버전
* 패키지 매니저와 lock 파일
* `vite.config.*`
* `tsconfig*.json`
* ESLint와 포매터 설정
* 테스트 설정
* 대상 코드와 인접한 코드
* 동일한 기능을 구현한 기존 코드
* 프로젝트 디렉터리 구조
* 라우팅, 상태 관리, 데이터 조회, 스타일링에 사용하는 도구
* 빌드 모드별 환경변수와 배포 환경

확인하지 않은 패키지나 API가 설치되어 있다고 가정하지 않는다.

패키지 매니저는 lock 파일을 기준으로 판단한다.

* `pnpm-lock.yaml`: pnpm
* `yarn.lock`: Yarn
* `package-lock.json`: npm
* `bun.lock` 또는 `bun.lockb`: Bun

프로젝트에서 사용 중인 패키지 매니저를 임의로 변경하지 않는다.

## 3. Vite 규칙

### 3.1 설정 유지

* 기존 `vite.config.*`와 플러그인 구성을 우선한다.
* 요청 없이 번들러, React 플러그인 또는 빌드 방식을 교체하지 않는다.
* `base`, `publicDir`, `resolve.alias`, `server.proxy`, `build` 설정을 변경하기 전에 배포 환경과 사용처를 확인한다.
* 설정 문제를 우회하기 위해 불필요한 플러그인을 추가하지 않는다.
* 애플리케이션 코드에서 Node.js 전용 API를 사용할 수 있다고 가정하지 않는다.

### 3.2 진입점과 정적 파일

* `index.html`은 Vite의 진입점으로 취급한다.
* React 진입 파일과 root element의 연결을 확인한다.
* 소스에서 import하여 번들링할 자산은 일반적으로 `src` 아래에 둔다.
* 원본 파일명 그대로 제공해야 하는 자산만 `public` 사용을 검토한다.
* `public` 자산은 소스 코드에서 import하지 않고 배포 기준 절대 경로로 참조한다.
* 배포 경로가 루트가 아닐 수 있다면 하드코딩된 `/` 경로와 `base` 설정의 영향을 확인한다.

### 3.3 환경변수

* 클라이언트 코드에서는 `import.meta.env`를 사용한다.
* 기본적으로 `VITE_` 접두사가 있는 값은 클라이언트 번들에 노출된다고 간주한다.
* 비밀키, 서버 토큰, 데이터베이스 접속 정보에 `VITE_` 접두사를 사용하지 않는다.
* `import.meta.env.MODE`, `DEV`, `PROD`, `BASE_URL` 등 내장 값의 의미를 임의로 바꾸지 않는다.
* 환경변수 접두사를 변경했다면 `envPrefix` 설정과 보안 영향을 확인한다.
* 환경변수 타입이 필요하면 기존 `vite-env.d.ts` 또는 프로젝트의 타입 선언 방식을 따른다.
* `.env` 파일과 비밀값을 저장소에 커밋하지 않는다.

### 3.4 개발 서버와 프록시

* 개발 서버 프록시는 로컬 개발 편의를 위한 설정이며 운영 API 게이트웨이를 대체하지 않는다.
* 프록시 경로를 변경할 때 API 클라이언트, 쿠키, CORS, WebSocket 사용 여부를 확인한다.
* 개발 환경에서만 동작하는 우회 코드를 애플리케이션 로직에 넣지 않는다.

### 3.5 코드 분할

* 라우트 또는 실제로 무거운 기능 단위에서 동적 import를 검토한다.
* 작은 컴포넌트를 무조건 lazy loading하지 않는다.
* `React.lazy`를 사용하면 적절한 `Suspense` fallback과 로딩 실패 처리를 함께 검토한다.
* `manualChunks`는 실제 번들 분석 결과와 캐시 전략을 근거로 설정한다.

## 4. 라우팅

* 프로젝트에서 사용하는 라우터와 버전을 먼저 확인한다.
* 요청 없이 라우터 라이브러리를 추가하거나 교체하지 않는다.
* 기존 라우트 정의 방식, 중첩 구조, loader 및 guard 패턴을 유지한다.
* URL 구조와 기능 구조가 자연스럽게 대응되도록 구성한다.
* 검색 조건, 필터, 페이지 번호처럼 공유하거나 새로고침 후 유지되어야 하는 값은 URL 상태를 우선 검토한다.
* 링크 이동에 일반 `<a>`와 라우터의 Link 컴포넌트 중 무엇이 적절한지 구분한다.
* 인증 UI만 숨기는 것을 라우트 또는 API 권한 검사로 간주하지 않는다.
* SPA를 직접 경로로 새로고침할 때 서버의 history fallback 설정이 필요한지 확인한다.
* 라우트 단위 코드 분할 시 로딩, 오류, 404 상태를 함께 처리한다.

## 5. 컴포넌트 설계

### 5.1 책임 분리

* 하나의 컴포넌트는 하나의 명확한 역할을 갖도록 한다.
* 페이지 컴포넌트가 세부 UI 구현까지 모두 담당하지 않도록 한다.
* 데이터 조회, 상태 관리, 표현 로직을 무조건 한 파일에 모으지 않는다.
* 단순히 파일을 줄이기 위한 의미 없는 컴포넌트 분리는 하지 않는다.
* 한 번만 사용되는 짧은 마크업을 반드시 별도 컴포넌트로 만들 필요는 없다.
* UI와 무관한 도메인 로직은 컴포넌트 밖의 테스트 가능한 단위로 분리할 수 있다.

### 5.2 이름

* React 컴포넌트는 PascalCase를 사용한다.
* 훅은 `use`로 시작한다.
* 이벤트 핸들러는 동작이 드러나는 이름을 사용한다.
* 불리언은 상태가 드러나는 이름을 사용한다.

```tsx
const isLoading = false;
const hasNextPage = true;
const canSubmit = true;

const handleSubmit = () => {};
const handleItemSelect = () => {};
```

`flag`, `data2`, `handle`처럼 의미가 불명확한 이름은 피한다.

### 5.3 Props

* Props 타입은 명시한다.
* 사용하지 않는 Props를 미리 추가하지 않는다.
* 지나치게 많은 불리언 Props 조합을 만들지 않는다.
* 상태 종류가 명확하다면 union 타입을 사용한다.
* 단순한 Props 전달을 피하기 위해 무조건 Context를 만들지 않는다.
* DOM 요소의 Props를 확장할 때는 React의 기본 타입을 활용한다.

```tsx
type ButtonProps = React.ComponentPropsWithoutRef<'button'> & {
    variant?: 'primary' | 'secondary';
};
```

### 5.4 합성

* 거대한 설정 객체 하나로 모든 UI를 제어하는 방식보다 컴포넌트 합성을 우선 검토한다.
* `children`과 명시적인 slot Props를 적절히 사용한다.
* 상속 기반 컴포넌트 구조는 사용하지 않는다.
* 공통 컴포넌트가 특정 기능의 상태 관리나 API 형태에 과도하게 의존하지 않도록 한다.

## 6. React 작성 규칙

### 6.1 렌더링 순수성

렌더링 중에는 부수 효과를 발생시키지 않는다.

* 렌더링 중 상태 변경
* 렌더링 중 네트워크 요청 실행
* 렌더링 중 DOM 직접 조작
* 렌더링 중 전역 변수 변경
* 렌더링 결과에 영향을 주는 임의의 `Date.now()` 또는 `Math.random()` 호출

부수 효과는 이벤트 핸들러 또는 필요한 Effect에서 처리한다.

### 6.2 Hook 규칙

* Hook은 컴포넌트 또는 커스텀 Hook의 최상위에서만 호출한다.
* 조건문, 반복문, 중첩 함수 내부에서 Hook을 호출하지 않는다.
* Hook 호출 순서가 렌더링마다 달라지지 않도록 한다.
* Effect 의존성 경고를 무시하지 않는다.
* 의존성 배열을 비우기 위해 ESLint 규칙을 비활성화하지 않는다.
* 커스텀 Hook은 재사용되는 상태 로직을 표현해야 하며 단순한 함수 감싸기로 만들지 않는다.

### 6.3 Effect 최소화

`useEffect`는 외부 시스템과 React 상태를 동기화할 때 사용한다.

적절한 사용 예:

* 브라우저 이벤트 구독
* 타이머 등록
* 외부 라이브러리 인스턴스 동기화
* DOM API 연동
* WebSocket 연결

다음 작업에는 Effect를 우선 사용하지 않는다.

* Props로부터 파생 상태 계산
* 배열 필터링 및 정렬
* 사용자 이벤트 처리
* 다른 상태가 변경됐다는 이유만으로 상태 복사
* 렌더링에 필요한 단순 계산

```tsx
// 지양
const [fullName, setFullName] = useState('');

useEffect(() => {
    setFullName(`${firstName} ${lastName}`);
}, [firstName, lastName]);

// 권장
const fullName = `${firstName} ${lastName}`;
```

### 6.4 메모이제이션

* `useMemo`, `useCallback`, `memo`를 습관적으로 사용하지 않는다.
* 실제 성능 문제나 참조 안정성이 필요한 경우에만 사용한다.
* 메모이제이션 적용 전 계산 비용과 리렌더링 원인을 확인한다.
* 단순한 함수 또는 값이라는 이유만으로 메모이제이션하지 않는다.
* 프로젝트에서 React Compiler를 사용한다면 해당 설정과 규칙을 우선한다.

### 6.5 상태 관리

상태는 필요한 가장 가까운 위치에 둔다.

상태 종류에 따라 다음 순서로 검토한다.

1. URL로 표현해야 하는 상태
2. 컴포넌트 로컬 상태
3. 상위 컴포넌트로 끌어올린 상태
4. Context
5. 프로젝트의 전역 상태 관리 도구
6. 서버 상태 전용 라이브러리의 캐시

* 서버에서 받은 데이터를 이유 없이 별도의 전역 상태에 복사하지 않는다.
* 서버 상태와 클라이언트 UI 상태를 구분한다.
* Context 값이 자주 변경되어 넓은 범위를 불필요하게 리렌더링하지 않는지 확인한다.
* 영속화가 필요한 상태만 저장소에 보관하고 버전 변경과 유효성 검증을 고려한다.

### 6.6 리스트와 key

* 안정적이고 고유한 식별자를 `key`로 사용한다.
* 항목의 삽입, 삭제, 재정렬이 가능한 목록에서 배열 index를 key로 사용하지 않는다.
* 렌더링할 때마다 생성되는 임의 값을 key로 사용하지 않는다.

## 7. 데이터 조회

### 7.1 기존 도구 우선

* 프로젝트에 TanStack Query, SWR, Apollo Client 등 기존 도구가 있다면 해당 도구를 우선 사용한다.
* 동일한 목적의 데이터 조회 라이브러리를 추가로 도입하지 않는다.
* 기존 API 클라이언트, base URL, 인증 헤더, 에러 변환 방식을 확인한다.
* 단순 조회를 위해 불필요하게 전역 상태 관리 도구를 사용하지 않는다.

### 7.2 요청 시점

* 화면 진입 시 필요한 데이터와 사용자 상호작용 이후 필요한 데이터를 구분한다.
* 서로 의존하지 않는 요청은 병렬로 처리한다.
* 두 번째 요청이 첫 번째 결과에 의존할 때만 순차 요청을 사용한다.
* 라우터가 loader를 지원하고 프로젝트에서 사용 중이라면 컴포넌트 Effect보다 기존 loader 패턴을 우선한다.
* 렌더링 본문에서 네트워크 요청을 직접 시작하지 않는다.

```tsx
const [user, products] = await Promise.all([
    getUser(),
    getProducts(),
]);
```

### 7.3 요청 생명주기

* 로딩, 오류, 빈 결과, 성공 상태를 구분한다.
* 컴포넌트가 unmount되거나 요청 조건이 바뀔 때 오래된 응답이 최신 상태를 덮지 않도록 한다.
* 직접 `fetch`를 제어할 때는 필요한 경우 `AbortController`를 사용한다.
* 중복 요청, 재시도, 캐시 만료 정책은 라이브러리 기본값을 추측하지 말고 기존 설정을 확인한다.
* 재시도해도 해결되지 않는 사용자 입력 오류를 무조건 재시도하지 않는다.

### 7.4 데이터 접근 계층

복잡한 프로젝트에서는 데이터 접근 로직을 UI와 분리한다.

```text
features/
  product/
    api/
    components/
    hooks/
    model/
    utils/
```

다음 로직은 페이지 JSX 내부에 직접 길게 작성하지 않는다.

* API 응답 변환
* 복잡한 필터링
* 권한별 데이터 가공
* 도메인 규칙
* 반복되는 요청 옵션

### 7.5 캐시와 변경

* 캐시 정책은 데이터의 최신성, 사용자 범위, 변경 빈도를 기준으로 결정한다.
* 인증별 데이터를 공용 cache key로 섞지 않는다.
* 생성, 수정, 삭제 후 관련 query의 무효화 또는 갱신이 필요한지 확인한다.
* optimistic update는 실패 시 복구 방식과 동시 변경 충돌을 함께 설계한다.
* 클라이언트 검증은 사용자 경험을 위한 것이며 API 서버의 검증과 권한 확인을 대체하지 않는다.

---

## 8. 타입스크립트

### 8.1 기본 규칙

* 가능한 엄격한 타입을 유지한다.
* `any` 사용을 피한다.
* 외부 입력은 `unknown`으로 받은 뒤 검증한다.
* 타입 단언보다 타입 좁히기를 우선한다.
* 사용되지 않는 타입과 import를 남기지 않는다.
* 타입 전용 import는 `import type`을 사용한다.
* 함수의 반환 타입은 추론이 명확하지 않거나 공개 API인 경우 명시한다.
* 런타임 값이 필요한 경우 `enum`보다 객체와 union 타입을 우선 검토한다.

```tsx
export const ORDER_STATUS = {
    Pending: 'pending',
    Completed: 'completed',
    Cancelled: 'cancelled',
} as const;

export type OrderStatus =
    (typeof ORDER_STATUS)[keyof typeof ORDER_STATUS];
```

### 8.2 타입 재사용

* 실제 도메인 의미가 같은 타입만 재사용한다.
* 형태가 우연히 같다는 이유로 다른 도메인의 타입을 재사용하지 않는다.
* API 응답 타입과 화면 모델이 다르면 변환 계층을 둔다.
* 거대한 공용 타입 파일에 모든 타입을 모으지 않는다.
* 타입은 사용하는 기능과 가까운 위치에 둔다.

### 8.3 외부 입력과 오류 억제

다음 값은 신뢰하지 않는다.

* URL parameter와 query string
* FormData와 API 응답
* 로컬 스토리지와 세션 스토리지 값
* `postMessage` 데이터
* 사용자 입력

프로젝트에 Zod, Valibot 등의 검증 도구가 있다면 기존 도구를 사용한다. 검증 도구가 없는 단순한 경우에는 새 의존성을 추가하기 전에 타입 가드를 검토한다.

`@ts-ignore`, `as any` 또는 광범위한 타입 단언으로 오류를 숨기지 않는다. 불가피하게 억제가 필요하면 가능한 좁은 범위에서 이유를 명시한다.

---

## 9. 오류 처리

### 9.1 예상 가능한 오류

다음과 같은 오류는 화면에서 처리 가능한 상태로 다룬다.

* 잘못된 사용자 입력
* 인증 실패와 권한 부족
* 존재하지 않는 데이터
* 비즈니스 규칙 위반
* 네트워크 연결 실패
* 중복 요청

사용자가 해결할 수 있는 오류에는 다음 행동을 알 수 있는 메시지를 제공한다.

### 9.2 예상하지 못한 오류

* 의미 없는 `try-catch`로 오류를 삼키지 않는다.
* 처리할 수 없는 오류는 상위 오류 경계 또는 기존 로깅 시스템으로 전달한다.
* 오류 메시지와 stack trace, 토큰, 내부 API 정보를 사용자에게 그대로 노출하지 않는다.
* Promise rejection을 방치하지 않는다.

```tsx
// 지양
try {
    await execute();
} catch {
    return null;
}
```

### 9.3 Error Boundary

* 렌더링 오류로 전체 앱이 빈 화면이 되지 않도록 적절한 경계에서 Error Boundary를 검토한다.
* 모든 작은 컴포넌트를 개별 Error Boundary로 감싸지 않는다.
* 이벤트 핸들러와 비동기 콜백의 오류가 Error Boundary에서 자동 처리된다고 가정하지 않는다.
* 오류 복구 UI에는 사용자가 다시 시도하거나 이동할 수 있는 방법을 제공한다.

## 10. 로딩과 Suspense

* 데이터 조회 시간이 긴 영역은 적절한 로딩 UI를 제공한다.
* 전체 화면을 하나의 거대한 로딩 경계로만 처리하지 않는다.
* 독립적으로 표시할 수 있는 영역은 별도 경계를 검토한다.
* 레이아웃 이동이 크지 않은 skeleton을 사용한다.
* 무조건 Suspense를 추가하지 않고 사용하는 데이터 도구와 렌더링 방식이 Suspense를 지원하는지 확인한다.
* lazy-loaded chunk가 실패했을 때 오류 처리 경로를 확인한다.

---

## 11. 폼

* 프로젝트에 React Hook Form 등 기존 폼 도구가 있다면 이를 따른다.
* 단순한 폼에 불필요한 라이브러리를 추가하지 않는다.
* 모든 입력을 무조건 `useState`로 관리하지 않는다.
* 제출 직전 데이터와 API 계약을 기준으로 입력값을 검증한다.
* 제출 중 중복 요청을 방지한다.
* 성공, 실패, 진행 중 상태를 사용자에게 전달한다.
* 오류 메시지는 관련 입력과 연결한다.
* 키보드만으로 폼을 사용할 수 있어야 한다.
* 버튼의 기본 `type`에 의존하지 않는다.

```tsx
<button type="submit">저장</button>
<button type="button">취소</button>
```

## 12. 스타일링

* 프로젝트에서 사용 중인 스타일 방식을 유지한다.
* Tailwind CSS, CSS Modules, CSS-in-JS 등을 임의로 혼용하지 않는다.
* 새로운 UI 라이브러리를 요청 없이 추가하지 않는다.
* 기존 디자인 토큰과 공통 컴포넌트를 우선 사용한다.
* 동일한 색상, 간격, 폰트 값을 여러 곳에 하드코딩하지 않는다.
* 전역 CSS는 실제 전역 스타일에만 사용한다.
* 컴포넌트 전용 스타일은 가능한 해당 컴포넌트와 가까운 위치에 둔다.
* `!important`로 우선순위 문제를 무조건 우회하지 않는다.
* 불필요하게 높은 `z-index`를 사용하지 않는다.
* 반응형 동작을 고려한다.
* hover에만 의존하여 핵심 정보를 전달하지 않는다.

Tailwind CSS를 사용하는 경우:

* 동적으로 조합되어 빌드 시 탐지되지 않는 클래스 문자열을 주의한다.
* 같은 클래스 조합이 반복될 때에만 공통화한다.
* 단순히 클래스 문자열을 줄이기 위한 추상화는 하지 않는다.
* 프로젝트에 클래스 병합 유틸리티가 있다면 기존 유틸리티를 사용한다.

## 13. 이미지와 폰트

### 13.1 이미지

* 의미 있는 이미지에는 목적에 맞는 `alt`를 제공한다.
* 장식용 이미지는 빈 `alt`를 사용한다.
* 레이아웃 이동을 방지하도록 크기 또는 비율을 지정한다.
* 첫 화면의 핵심 이미지에만 우선 로딩을 검토한다.
* 화면 밖 이미지에는 필요한 경우 native lazy loading을 사용한다.
* 반응형 이미지가 필요하면 `srcSet`, `sizes`, `<picture>`를 검토한다.
* 단순 아이콘은 프로젝트의 아이콘 시스템을 따른다.
* Vite의 asset import와 `public` 경로를 혼동하지 않는다.

### 13.2 폰트

* 프로젝트에서 사용하는 폰트 로딩 방식을 유지한다.
* 필요한 font weight와 subset만 로드한다.
* 시스템 폰트로 충분한 경우 불필요한 웹 폰트를 추가하지 않는다.
* 웹 폰트가 초기 렌더링과 레이아웃 이동에 미치는 영향을 확인한다.

## 14. 문서 metadata와 SEO

공개 페이지는 필요한 metadata를 제공한다.

* 고유한 `title`과 `description`
* canonical URL
* Open Graph 정보
* 필요한 경우 소셜 카드와 robots 정책

* SPA에서 라우트별 metadata가 필요하면 프로젝트의 기존 head 관리 방식을 따른다.
* 모든 페이지에 동일한 title을 사용하지 않는다.
* 사용자 입력을 검증 없이 metadata에 삽입하지 않는다.
* 클라이언트 렌더링 SPA만으로 검색 노출 요구를 충족할 수 있는지 별도로 확인한다.
* SSR, SSG 또는 prerendering이 필요하다면 React+Vite만으로 해결된다고 가정하지 말고 배포 구조를 확인한다.

## 15. 접근성

접근성은 선택 기능이 아니라 기본 요구사항으로 취급한다.

* 의미에 맞는 HTML 요소를 사용한다.
* 클릭 가능한 `div` 대신 `button` 또는 `a`를 사용한다.
* 모든 입력에 연결된 label을 제공한다.
* 키보드로 모든 핵심 기능을 사용할 수 있어야 한다.
* focus 표시를 제거하지 않는다.
* 모달이 열리면 focus 이동, focus trap, focus 복귀를 고려한다.
* 색상만으로 상태를 구분하지 않는다.
* 아이콘 버튼에는 접근 가능한 이름을 제공한다.
* 이미지에 적절한 `alt`를 제공한다.
* heading 순서를 의미에 맞게 구성한다.
* ARIA는 기본 HTML만으로 의미를 표현할 수 없을 때 사용한다.
* `aria-label`로 잘못된 HTML 구조를 감추지 않는다.
* 비동기 상태 변경을 보조 기술에 알려야 하는지 확인한다.
* 애니메이션에는 `prefers-reduced-motion`을 고려한다.

## 16. 보안

### 16.1 클라이언트 경계

React+Vite 애플리케이션의 코드는 사용자 브라우저에 전달된다고 간주한다.

* 클라이언트 번들에 비밀값을 포함하지 않는다.
* 프런트엔드의 권한 분기와 입력 검증을 서버 보안으로 간주하지 않는다.
* 소스맵 공개 여부와 오류 수집 도구의 민감정보 전송을 확인한다.
* 인증 토큰 저장 방식은 기존 보안 설계를 따르고 임의로 변경하지 않는다.

### 16.2 외부 입력과 출력

* 사용자 입력과 외부 API 응답을 검증한다.
* `dangerouslySetInnerHTML`은 불가피한 경우에만 사용한다.
* HTML을 출력해야 한다면 검증된 방식으로 정화한다.
* 외부 URL 이동은 허용 대상을 검증한다.
* `target="_blank"` 사용 시 opener 보안을 확인한다.
* 사용자 제공 값을 코드, 스타일, URL 문맥에 검증 없이 삽입하지 않는다.
* 파일 업로드는 확장자와 클라이언트의 MIME type만 신뢰하지 않는다.

### 16.3 API와 인증

* UI에서 버튼을 숨기는 것은 권한 검사가 아니다.
* API 서버가 인증, 권한, 입력값을 다시 검증해야 한다.
* CORS는 인증이나 권한 제어를 대체하지 않는다.
* CSRF 방어가 필요한 인증 방식인지 서버 구성과 함께 확인한다.
* 내부 오류, stack trace, 토큰을 화면이나 로그에 노출하지 않는다.

## 17. 성능

성능 최적화는 측정 가능한 문제를 기준으로 수행한다.

우선 확인할 항목:

* 큰 초기 JavaScript 번들
* 순차적인 데이터 요청과 중복 요청
* 과도한 리렌더링
* 큰 이미지와 웹 폰트
* 불필요한 third-party script
* 화면 밖 콘텐츠의 초기 렌더링
* 레이아웃 이동
* 메인 스레드를 오래 점유하는 계산

권장 원칙:

* React DevTools Profiler와 번들 분석 결과를 근거로 개선한다.
* 무거운 화면과 기능은 필요할 때 동적 import를 검토한다.
* 독립적인 요청은 병렬화한다.
* 큰 목록은 pagination 또는 virtualization을 검토한다.
* 모든 컴포넌트에 메모이제이션을 적용하지 않는다.
* tree shaking을 방해하는 import와 side effect 설정을 확인한다.
* 성능을 위해 가독성과 정확성을 과도하게 희생하지 않는다.

## 18. 디렉터리 구조

기존 프로젝트 구조를 우선한다.

새 구조가 필요한 경우 기능 단위 구성을 우선 검토한다.

```text
src/
  app/
    providers/
    router/
  features/
    product/
      api/
      components/
      hooks/
      model/
      utils/
  components/
    ui/
  lib/
  styles/
```

각 디렉터리의 기본 역할:

* `app`: 앱 진입점, 전역 provider, 라우터와 전역 설정
* `features`: 도메인 또는 기능별 코드
* `components/ui`: 여러 기능에서 사용하는 표현 중심 UI
* `lib`: 특정 기능에 종속되지 않은 인프라 및 공통 설정
* `styles`: 전역 스타일과 공용 스타일 설정

다음 구조는 피한다.

* 역할이 불분명한 거대한 `utils` 디렉터리
* 모든 타입을 모은 거대한 `types.ts`
* 모든 API를 모은 단일 `api.ts`
* 기능과 무관하게 파일 종류만으로 지나치게 분리한 구조
* 실제 재사용되지 않는 공통 컴포넌트

파일을 공통 영역으로 이동하기 전에 실제로 여러 기능에서 같은 의미로 사용되는지 확인한다.

## 19. 유틸리티와 추상화

* 두세 줄의 단순 코드를 숨기기 위한 유틸리티를 무조건 만들지 않는다.
* 한 번만 사용되는 로직을 미래 재사용 가능성만으로 추상화하지 않는다.
* 이름만 다른 wrapper 함수를 만들지 않는다.
* 공통화 전에 코드의 형태뿐 아니라 의미가 같은지 확인한다.
* 추상화가 조건문과 옵션을 계속 늘린다면 기능별 구현 분리를 검토한다.
* 잘못된 추상화를 유지하기 위해 복잡한 타입을 만들지 않는다.

추상화는 다음 조건 중 하나를 만족할 때 검토한다.

* 동일한 도메인 규칙이 반복된다.
* 변경 시 여러 위치를 반드시 함께 수정해야 한다.
* 복잡한 구현 세부사항을 감출 필요가 있다.
* 테스트 가능한 독립 단위가 된다.

## 20. 주석, 문서, 로깅

### 20.1 주석과 문서

* 코드가 무엇을 하는지 그대로 설명하는 주석은 작성하지 않는다.
* 코드만으로 알기 어려운 이유와 제약을 설명한다.
* 임시 해결책에는 원인과 제거 조건을 작성한다.
* 외부 시스템의 제약으로 인한 코드라면 해당 이유를 남긴다.
* 코드 변경 후 더 이상 맞지 않는 주석은 함께 수정하거나 제거한다.
* 요청하지 않은 장문의 JSDoc을 모든 함수에 추가하지 않는다.

### 20.2 로깅

* 디버깅용 `console.log`를 최종 코드에 남기지 않는다.
* 운영 로그와 오류 보고는 프로젝트의 기존 도구를 사용한다.
* 비밀번호, 토큰, Cookie, 개인정보를 로그에 기록하지 않는다.
* 동일한 오류를 여러 계층에서 중복 기록하지 않는다.
* 사용자에게 표시하는 메시지와 운영 로그 메시지를 구분한다.

## 21. 테스트

### 21.1 기본 원칙

* 구현 세부사항보다 사용자에게 보이는 동작을 검증한다.
* 테스트를 통과시키기 위해 실제 동작을 왜곡하지 않는다.
* 테스트마다 검증 목적을 명확하게 유지한다.
* 하나의 테스트에 서로 무관한 시나리오를 지나치게 많이 넣지 않는다.
* 기존 테스트 도구를 우선 사용한다.
* 요청 없이 테스트 프레임워크를 교체하거나 추가하지 않는다.
* Vite 프로젝트라고 Vitest를 사용한다고 가정하지 않고 설정과 scripts를 확인한다.

### 21.2 Given-When-Then

```tsx
it('입력한 검색어로 상품을 조회한다', async () => {
    // Given
    const user = userEvent.setup();
    render(<SearchForm onSubmit={onSubmit} />);

    // When
    await user.type(screen.getByRole('textbox'), '키보드');
    await user.click(screen.getByRole('button', { name: '검색' }));

    // Then
    expect(onSubmit).toHaveBeenCalledWith('키보드');
});
```

### 21.3 검증 대상

우선 검증할 항목:

* 사용자 상호작용과 조건에 따른 UI 변화
* 입력값 검증
* 권한별 화면 동작
* 오류, 로딩, 빈 상태
* 데이터 변환과 비즈니스 규칙
* 접근 가능한 역할과 이름
* 회귀 가능성이 높은 동작

가치가 낮을 수 있어 목적을 확인할 테스트:

* 컴포넌트가 단순히 render된다는 테스트
* 내부 state 값 직접 검증
* 구현 함수 호출 횟수만 검증
* 변경에 지나치게 민감한 대형 snapshot
* 라이브러리 자체 동작 검증
* 타입 시스템으로 이미 보장되는 내용 검증

### 21.4 Mock과 테스트 범위

* 네트워크, 시간, 브라우저 API, 외부 서비스 등 필요한 경계만 mock한다.
* 내부 구현 함수를 과도하게 mock하지 않는다.
* Mock이 실제 API 형태와 달라지지 않도록 관리한다.
* 테스트 간 mock 상태를 공유하지 않는다.
* 네트워크 mock에는 프로젝트의 기존 도구를 사용한다.
* 순수 함수는 단위 테스트, 컴포넌트 상호작용은 컴포넌트 테스트, 핵심 사용자 흐름은 E2E 테스트를 검토한다.
* 모든 변경에 모든 종류의 테스트를 추가할 필요는 없다.

## 22. ESLint, TypeScript, 테스트, 빌드 검증

작업 완료 후 `package.json`의 scripts를 확인하여 가능한 범위에서 실행한다.

우선순위:

1. 변경 파일 관련 테스트
2. TypeScript 검사
3. ESLint
4. 전체 테스트
5. Vite 프로덕션 빌드

명령어를 추측하지 않는다.

```bash
pnpm test
pnpm type-check
pnpm lint
pnpm build
```

모노레포에서는 변경 대상 패키지 또는 앱 범위로 실행할 수 있는 명령을 우선 사용한다.

검증에 실패하면:

* 기존 오류인지 이번 변경으로 발생한 오류인지 구분한다.
* 관련 없는 기존 오류를 요청 없이 모두 수정하지 않는다.
* 실행하지 못한 검증은 실행한 것처럼 말하지 않는다.
* 실패 내용을 숨기지 않는다.
* 빌드 성공만으로 브라우저 런타임 동작이 검증됐다고 간주하지 않는다.

## 23. 의존성 관리

새 패키지를 추가하기 전에 확인한다.

* 기존 패키지나 Web API로 해결 가능한가
* 프로젝트 내 유사 기능이 있는가
* 패키지 크기와 초기 번들 영향은 어떤가
* tree shaking을 지원하는가
* 유지보수 상태와 라이선스가 적절한가
* 현재 React, Vite, TypeScript 버전을 지원하는가

요청 없이 다음 작업을 하지 않는다.

* 패키지 매니저 변경
* lock 파일 전체 재생성
* 주요 버전 일괄 업데이트
* 여러 라이브러리 동시 교체
* npm, Yarn, pnpm 명령 혼용
* 이미 사용 중인 라이브러리와 같은 목적의 패키지 추가

패키지를 추가했다면 실제로 필요한 최소 범위에서 사용한다.

---

## 24. 모노레포와 공통 패키지

모노레포인 경우 다음을 확인한다.

* workspace 설정과 루트 및 앱별 `package.json`
* 패키지 경계와 내부 패키지의 export
* TypeScript project reference 또는 path alias
* Vite의 alias와 TypeScript 경로 설정의 일치 여부
* 빌드 도구 설정과 패키지별 React 및 Vite 버전
* peer dependency
* 브라우저 코드에 Node.js 전용 코드가 유입되는지 여부

공통 UI 패키지는 가능한 다음 특성을 유지한다.

* 특정 앱의 환경변수에 직접 의존하지 않는다.
* 특정 앱의 라우터나 상태 관리 도구에 불필요하게 의존하지 않는다.
* React를 중복 번들링하지 않도록 설정을 확인한다.
* 공개 API를 명확한 export로 제공한다.
* 외부 소비자가 내부 파일 경로를 직접 import하지 않도록 한다.
* 라이브러리 빌드라면 `react`와 `react-dom`의 external 및 peer dependency 구성을 확인한다.

## 25. 코드 수정 규칙

* 대상 기능과 관련된 파일만 수정한다.
* 요청 없이 파일명과 디렉터리를 대량 변경하지 않는다.
* 요청 없이 import 순서만 바꾸는 변경을 만들지 않는다.
* 포매터 때문에 관련 없는 파일 전체가 변경되지 않도록 한다.
* 공개 API 변경 시 사용처를 함께 확인한다.
* 함수 시그니처 변경 시 모든 호출부를 확인한다.
* 타입 변경 시 런타임 데이터 형태도 함께 확인한다.
* 삭제한 코드의 import, 타입, 테스트, 스타일을 정리한다.
* 기존 동작을 변경한다면 변경 의도가 테스트 또는 코드에서 드러나게 한다.

## 26. 금지되는 패턴

명확한 이유 없이 다음 패턴을 사용하지 않는다.

* 모든 데이터를 개별 컴포넌트 Effect에서 조회
* Props를 state로 불필요하게 복사
* 파생 값을 Effect로 동기화
* 모든 함수에 `useCallback` 적용
* 모든 값에 `useMemo` 적용
* 배열 index 또는 임의 값을 안정적인 key처럼 사용
* 사용자 입력과 외부 API 응답을 검증 없이 사용
* 클라이언트에서만 인증과 권한 검사
* 비밀값을 `VITE_` 환경변수로 노출
* `any`와 광범위한 타입 단언으로 타입 오류 우회
* 빈 `catch` 블록 또는 오류를 무조건 `null`로 변환
* 의미 없는 wrapper 컴포넌트 생성
* 미래 요구사항을 위한 과도한 추상화
* 요청하지 않은 의존성 추가와 대규모 리팩터링
* 타입 검사 또는 ESLint 규칙 비활성화
* 디버깅용 로그와 오래된 주석 방치
* 테스트를 통과시키기 위한 실제 로직 왜곡
* Vite 개발 서버에서 동작한다는 이유만으로 운영 배포 경로와 서버 설정을 무시

## 27. 작업 완료 기준

### 기능

* 요청된 동작이 구현되었는가
* 기존 동작이 불필요하게 변경되지 않았는가
* 로딩, 오류, 빈 상태가 필요한가
* 엣지 케이스가 처리되었는가

### React와 Vite

* Effect가 외부 시스템 동기화에만 필요한 만큼 사용되었는가
* state가 필요한 가장 가까운 위치에 있는가
* 서버 상태와 UI 상태가 불필요하게 중복되지 않는가
* 데이터 요청 waterfall과 오래된 응답 경쟁이 없는가
* 환경변수와 비밀값의 경계가 지켜졌는가
* asset 경로와 SPA fallback이 배포 환경에서 동작하는가
* 불필요한 초기 번들과 동적 import가 추가되지 않았는가

### 타입과 보안

* `any` 또는 과도한 타입 단언이 추가되지 않았는가
* 외부 입력을 검증했는가
* API 서버의 인증과 권한 확인을 전제로 했는가
* 비밀값과 내부 오류 정보가 클라이언트에 노출되지 않는가

### UI

* 키보드로 사용할 수 있는가
* 적절한 HTML 요소를 사용했는가
* 로딩 중 레이아웃 이동이 과도하지 않은가
* 모바일과 데스크톱에서 문제가 없는가
* 접근 가능한 이름과 label이 제공되는가

### 품질

* 관련 테스트를 추가하거나 수정했는가
* 변경 범위의 테스트가 통과하는가
* 타입 검사와 ESLint가 통과하는가
* 프로덕션 빌드가 통과하는가
* 불필요한 코드와 로그가 남아 있지 않은가
* 관련 없는 파일이 변경되지 않았는가

## 28. 응답 형식

코드 작업 결과를 설명할 때는 다음 내용을 중심으로 간결하게 작성한다.

* 변경한 내용
* 중요한 설계 판단
* 실행한 검증
* 남아 있는 문제 또는 확인하지 못한 사항

실행하지 않은 테스트나 빌드를 실행했다고 표현하지 않는다.

불필요한 작업 과정, 반복적인 요약, 형식적인 마무리 문장은 작성하지 않는다.
