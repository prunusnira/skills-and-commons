# /commit

입력: `$ARGUMENTS`

## 목적

현재 작업 디렉터리의 스테이지된/미스테이지된 변경사항을 분석해 커밋 메시지를 자동 작성하고 커밋을 생성한다. 옵션에 따라 push, squash rebase를 함께 수행한다.

## 인자 파싱

`$ARGUMENTS`에서 아래 값을 추출한다:

- `--push`: 커밋 후 `git push` 실행. 현재 브랜치가 upstream에 없으면 `git push -u origin {현재브랜치}` 로 설정 후 push
- `--rebase {N}`: 커밋 생성 후, 방금 만든 커밋을 포함해 최근 N개 커밋을 리베이스로 1개로 병합. 커밋 메시지는 병합된 N개 커밋의 내용을 종합해 본 문서의 커밋 메시지 형식에 맞게 새로 작성
- `--wip`: 작업 중임을 표시. 티켓 ID 추출 대신 커밋 메시지 맨 앞을 `[WIP]` 로 시작. 본문은 "현재 작업 중인 내용" 요약. `--rebase`와 함께 사용하면 rebase 대상 커밋들도 `[WIP]` 형식으로 통일

예시:
- `/commit` → 커밋만 생성
- `/commit --push` → 커밋 후 push
- `/commit --rebase 3` → 커밋 후 최근 3개 커밋을 1개로 squash
- `/commit --push --rebase 2` → 커밋 후 최근 2개 병합, push
- `/commit --wip` → `[WIP]` 접두어 커밋
- `/commit --wip --push` → WIP 커밋 후 push

## 1단계: 사전 검증

아래 조건 중 하나라도 해당하면 중단하고 사실을 알린다.

1. **현재 브랜치가 main/master인 경우** - 실수 방지. 진행 중지
2. **변경사항이 없는 경우** - `git status --porcelain`이 비어있으면 "커밋할 변경사항이 없습니다" 출력 후 중단
3. **머지 충돌이 남아있는 경우** - `git status`에 unmerged 경로가 있으면 중단

## 2단계: 변경사항 수집

병렬로 아래 명령을 실행한다:

- `git status --porcelain` - 스테이지/워킹트리 상태
- `git diff --staged` - 스테이지된 변경 (없으면 워킹트리 전체 diff로 대체)
- `git diff` - 미스테이지 변경
- `git log -5 --pretty=format:'%h %s'` - 최근 커밋 메시지 스타일 참고
- `git rev-parse --abbrev-ref HEAD` - 현재 브랜치명

### 스테이징 전략

- 스테이지된 변경이 있으면 그것만 커밋한다 (사용자가 의도적으로 스테이징한 것으로 간주)
- 스테이지된 변경이 없고 워킹트리에만 변경이 있으면, 사용자에게 확인 후 `git add -A` 대신 변경된 파일들을 개별적으로 `git add {파일경로}` 로 스테이징. 단 `.env`, `*.local`, credentials 파일이 포함되면 경고 후 제외

## 3단계: 티켓 ID 추출 또는 WIP 모드

`--wip` 플래그가 있으면 이 단계를 건너뛰고 4단계에서 `[WIP]` 형식으로 메시지를 작성한다.

`--wip`가 없으면 아래 순서로 티켓 ID를 결정한다:

1. 현재 브랜치명에서 `\S-\d+` 패턴 추출
2. 실패하면 가장 최근 커밋 메시지에서 `[\S-\d+]` 패턴 추출
3. 둘 다 실패하면 사용자에게 티켓 ID를 직접 물어본다 (CLAUDE.md 3번 - 추정 금지)

## 4단계: 커밋 메시지 작성

한국어로 작성. `--wip` 플래그 여부에 따라 형식이 다르다.

### 기본 형식 (`--wip` 없음)

CLAUDE.md 4번 Git 규칙을 따른다.

```
[{티켓ID}] {작업 요약 1줄}


{변경 내용 상세. 불릿 목록. 각 항목은 "무엇을, 왜"를 명시}

- {변경 항목 1}
- {변경 항목 2}
- {변경 항목 3}
```

### WIP 형식 (`--wip` 지정 시)

티켓 ID 대신 `[WIP]`를 사용한다.

```
[WIP] {현재 작업 중인 내용 요약 1줄}


{작업 중인 변경 내용. 불릿 목록}

- {변경 항목 1}
- {변경 항목 2}
```

WIP 커밋은 작업이 완료되지 않은 중간 저장 상태임을 명시. 완벽한 정리보다 현재 진행 중인 작업의 방향성과 변경 맥락을 빠르게 기록하는 것에 초점을 둔다.

### 작성 규칙

- **첫 줄**: `[티켓ID] 핵심 변경 대표 명사` (20~50자). 파일 단위가 아닌 기능 단위 요약
- **빈 줄 2개**: 첫 줄과 본문 사이에 반드시 빈 줄 2개
- **본문**: 기능/변경 단위로 불릿 분리. 단순 import 정리, 포맷 변경은 한 줄로 묶음
- 새 의존성, 환경 설정 변경, breaking change는 반드시 명시
- diff에서 파악한 핵심만. 추정 금지 (CLAUDE.md 3번)

### 예시

```
[JOB-1234] 장바구니 상품 삭제 시 스크롤 리셋 현상 수정


- CartPopUp 렌더 가드에서 isFetching 조건 제거로 삭제 API 호출 중에도 기존 리스트 유지
- deleteSelectedGoods, deleteSoldOutGoods의 중복 refetch 호출 제거 (각 2회 → 1회)
```

## 5단계: pre-commit 검증 (선택)

프로젝트에 husky/lint-staged 등 pre-commit 훅이 설정되어 있으면 그대로 실행되도록 `--no-verify` 없이 커밋. 훅 실패 시 원인을 출력하고 중단 (CLAUDE.md 4번 - --no-verify 금지).

## 6단계: 커밋 실행

```bash
git commit -m "$(cat <<'EOF'
{작성한 커밋 메시지}
EOF
)"
```

`-S`(GPG 서명)는 사용자 설정을 따름 (명시하지 않음).

## 7단계: Squash Rebase (`--rebase N` 지정 시만)

`--rebase` 플래그가 있을 때만 실행. **반드시 6단계에서 새 커밋이 정상적으로 생성된 이후에 실행한다.** 커밋 생성 실패 시 rebase 단계는 진행하지 않는다.

### 검증

- N은 2 이상의 정수여야 함. 1이거나 숫자가 아니면 에러 후 중단
- `git log`로 현재 커밋 포함 최근 N개가 모두 현재 브랜치의 커밋인지 확인 (다른 브랜치 커밋이나 머지 커밋이 포함되면 중단 후 사용자 확인)
- 현재 브랜치가 main/master이면 중단

### 메시지 재작성

최근 N개 커밋(방금 만든 커밋 포함)의 메시지와 diff를 모두 수집해서 종합 커밋 메시지를 새로 작성. 형식은 4단계와 동일하게 `[티켓ID] 요약` + 빈 줄 2개 + 불릿 본문. `--wip`가 같이 지정되었으면 `[WIP] 요약` 형식 사용.

### 실행

주의: 아래 `reset --soft`는 방금 6단계에서 만든 커밋이 HEAD에 존재하는 상태에서 실행된다. 커밋 생성 없이 바로 reset을 시도하지 않는다.

```bash
git reset --soft HEAD~{N}
git commit -m "$(cat <<'EOF'
{종합한 새 커밋 메시지}
EOF
)"
```

`git rebase -i` 대신 `reset --soft` + `commit` 조합을 사용하는 이유: 인터랙티브 모드 없이 안전하게 squash 가능.

주의: `reset --soft`는 되돌리기 어려운 작업. 실행 전 사용자에게 N개 커밋 목록과 함께 확인 (CLAUDE.md 3번).

## 8단계: Push (`--push` 지정 시만)

`--push` 플래그가 있을 때만 실행.

```bash
git push -u origin {현재브랜치}
```

upstream이 이미 설정되어 있으면 일반 `git push`.

main/master로는 절대 push하지 않음 (1단계에서 이미 차단).

## 9단계: 보고

완료 후 아래만 짧게 출력:

- 생성/수정된 커밋 해시 (짧은 형식)
- 커밋 메시지 첫 줄
- `--rebase` 사용 시: 병합된 커밋 수 (N → 1)
- `--push` 사용 시: push된 브랜치명

본문을 다시 출력하지 않는다 (CLAUDE.md 1번 - 응답 방식).

## 유의사항

- `git reset --soft`, `git push`는 되돌리기 어려운 작업. 실행 전 사용자 확인 필수 (CLAUDE.md 3번)
- force push는 절대 사용하지 않음 (CLAUDE.md 4번)
- `--no-verify` 절대 사용하지 않음 (CLAUDE.md 4번). pre-commit 훅 실패 시 원인 진단 후 수정
- 스테이징 전략: 사용자가 이미 스테이지한 파일이 있으면 그것만 존중. 자동 `git add -A` 금지
- `.env`, credentials, 시크릿 파일이 변경에 포함되면 커밋 중단 후 경고
