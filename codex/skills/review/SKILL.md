# 코드 리뷰 리포트

코드 리뷰 도구의 종류와 무관하게 이 스킬을 적용한다. OCR 기반 리뷰라면 `.claude/commands/ocr.md`의 실행 절차를 먼저 따르고, 결과 분류와 리포트 작성에는 이 스킬을 사용한다.

## 저장 위치

리뷰 결과는 반드시 `.claude/review/` 아래에 단일 HTML 파일로 저장한다. 디렉터리가 없으면 먼저 생성하고, 파일명은 `{YYYYMMDD-HHMMSS}-{tool}-{ref}.html` 형식을 사용한다. 이슈가 없거나 도구 오류가 있어도 결과 HTML을 저장한다. 리뷰를 실행하지 않는 미리보기 모드만 예외로 HTML을 저장하지 않는다.

## 공통 처리 절차

미리보기가 아닌 모든 리뷰는 아래 순서로 처리한다.

1. 리뷰 대상 변경사항을 확인하고 리뷰를 수행한다.
2. 발견 사항을 근거와 함께 1~4단계로 분류한다.
3. 이슈가 없거나 파싱·도구 오류가 발생한 경우도 결과를 한국어 HTML로 작성한다.
4. HTML을 `.claude/review/{YYYYMMDD-HHMMSS}-{tool}-{ref}.html`에 저장한다.
5. 저장한 파일 경로와 단계별 이슈 수를 짧게 보고한다.

## 리뷰 원칙

- 실제 변경 코드와 확인 가능한 근거를 먼저 검토한다. 근거가 부족하면 `확실하지 않음` 또는 `추측`으로 표시하고 사실처럼 단정하지 않는다.
- 스타일 선호, 합의된 정책과 무관한 제안, 재현할 수 없는 우려는 이슈로 과도하게 기록하지 않는다.
- 각 이슈에는 영향 범위, 발생 조건, 근거가 되는 파일·줄, 권장 조치를 간결하게 포함한다.
- 같은 근본 원인의 코멘트는 하나로 묶고, 높은 단계부터 제시한다.

## 4단계 중요도

모든 발견 사항을 아래 네 단계 중 하나로 분류한다.

1. **1단계 — 수정 불필요·사소함·추천 변경**
   - 수정이 필요 없거나 사소한 부분, 가독성·유지보수성 개선을 위한 추천 변경사항이다.
   - 수정하지 않아도 동작이나 안정성에 실질적인 영향이 없다.

2. **2단계 — 낮은 중요도의 버그**
   - 영향 범위가 작고 수정하지 않아도 서비스·기능에 큰 영향이 없는 버그다.
   - 다음 정비 시점에 수정하도록 권장한다.

3. **3단계 — 중간 중요도의 버그**
   - 실제 기능 오류, 잘못된 결과, 특정 조건의 사용자 영향 등이 생길 수 있는 버그다.
   - 배포 전 또는 가까운 시점에 수정하는 것을 권장한다.

4. **4단계 — 높은 중요도의 버그**
   - 데이터 손실·손상, 보안 문제, 서비스 중단, 광범위한 사용자 오류처럼 심각한 영향이 예상되는 버그다.
   - 반드시 수정한 뒤 진행해야 한다.

발생 가능성뿐 아니라 사용자·데이터·보안·서비스에 미치는 실제 영향을 함께 고려한다. 불확실하면 근거와 불확실성을 명시하고 높은 단계로 단정하지 않는다.

## 리포트 형식

1. **요약**: 리뷰 범위와 단계별 이슈 수를 적는다. 이슈가 없으면 그 사실을 명시한다.
2. **발견 사항**: 4단계부터 1단계 순으로 적는다.
   - 제목: `[N단계] 짧은 문제 요약`
   - 위치: 파일 경로와 줄 범위. 알 수 없으면 `파일 전체`
   - 근거와 영향: 발생 조건과 예상되는 문제
   - 권장 조치: 필요한 수정 또는 확인 방법
3. **미확인 사항·경고**: 도구 경고나 검증하지 못한 부분을 이슈와 분리해 적는다.

인라인 CSS만 사용해 브라우저에서 바로 열 수 있는 단일 HTML로 작성한다. 리뷰 도구의 원문을 그대로 복사하거나, 토큰·인증 정보 같은 민감 정보를 포함하지 않는다.
